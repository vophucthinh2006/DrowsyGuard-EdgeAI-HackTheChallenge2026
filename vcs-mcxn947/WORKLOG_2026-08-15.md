Session covered two phases: (1) simplifying the firmware to match the
system block diagram exactly, and (2) a full hardware bring-up debugging

## Phase 2 — BTS7960 motor bring-up + PWM1 debugging

Started from: `state=RUN`, correct duty cycles computed in software, but
**zero volts** on motor M+/M- terminals and a real physical buzzer making no
sound.

### Simplified test mode added first

Per request, added a "tap SW2 = motor runs, tap SW3 = stop" latching test
mode in `main.c`'s `ControlTask` (`s_motorLatchedOn`, toggled on gas/brake
button edges) to validate the BTS7960 hardware directly, bypassing the full
vehicle-control ramp logic. (Fixed an edge-detection ordering bug introduced
while wiring this up: `prevGas`/`prevBrake` were being updated *before* the
edge check instead of after, making the latch toggle never fire — moved the
`prevGas = gas; prevBrake = brake;` assignment to run after both edge
checks.)

### 2-phase raw-GPIO-then-PWM isolation test

Added `Alerts_RunPinBringupTest()` in `alerts.c`: phase 1 reconfigures the
buzzer pin (PORT2 pin 2, J3-7) as plain GPIO and toggles it 1 Hz for 10 s
(no PWM1 involved at all); phase 2 restores the PWM1_A2 pin config and
turns the buzzer on continuously. Result: **phase 1 audible, phase 2
silent** — isolated the bug specifically to PWM1, ruling out pin/wiring/
board-level causes.

### Reference example cross-check

Built and flashed the MCUXpresso SDK's own **unmodified**
`driver_examples/pwm/pwm_3ph` example directly (bypassing this project's
codebase). Confirmed audible PWM output on the same physical buzzer —
proved hardware/board/SDK were all fine, and the bug had to be in this
project's own source.

### Root cause found and fixed

Added a live PWM1 register dump to the phase-2 test. Found
`PWM1->SM[2].DISMAP[0] == 0xFFFF` (silicon reset default — not something
this project's code had set) mapping all 4 fault inputs to disable every
PWM1 output on every submodule, combined with those fault inputs floating
high (unconnected — this design has no fault sensors) and the default
combinational fault path being live. `FCTRL`/`FSTS`/`DISMAP` are PWM1-
module-wide, explaining why buzzer *and* all motor channels were silent at
once. Full analysis in
[`PWM_FAULT_BUG_POSTMORTEM.md`](./PWM_FAULT_BUG_POSTMORTEM.md).

**Fix:** `board_port/cm33_core0/hardware_init.c` now explicitly clears
`PWM1->SM[0..3].DISMAP[0] = 0U` right after the PWM1 sub-clock enables.

**Verification so far:** rebuilt (`-Werror`, 0 warnings), reflashed,
captured two independent serial register dumps confirming `OUTEN`/`MCTRL`/
duty registers (`VAL3 = 25000`, 50% of a 50000-tick period) and `DISMAP`'s
functional bits all read back correct. **Audible confirmation on real
hardware is still pending** as of this writeup.

### Other real (if minor) bugs found and fixed along the way

- `SYSCON->PWM1SUBCTL` was only enabling sub-clocks for 3 submodules
  (`CLK0_EN|CLK1_EN|CLK2_EN`) while this project actually uses 4
  (SM0/1/2/3 — SM3 borrowed for the right motor's LPWM since SM1's own B
  channel isn't header-accessible). Added `CLK3_EN`. Real bug, but
  insufficient alone to explain full silence — see postmortem.
- Missing WWDT0 functional clock, found earlier by flashing to hardware:
  without it, `WWDT_Init()`'s internal wait-for-clock spin hung boot
  silently. Fixed with `CLOCK_SetClkDiv(kCLOCK_DivWdt0Clk, 1U)` +
  `SYSCON_CLOCK_CTRL_FRO1MHZ_CLK_ENA_MASK` in `hardware_init.c`.
